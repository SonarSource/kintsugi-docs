    User Workflows¶

    This guide demonstrates common workflows and use cases for Kintsugi. Each workflow shows step-by-step how to accomplish typical development tasks.

    Basic Development Workflow¶

    The fundamental workflow for using Kintsugi with Claude Code.

    Steps¶

    1. Open Kintsugi
    2. Launch the application

    3. Backend and SonarLint Bridge start automatically

    4. Open Terminal

    5. Click terminal button or press Ctrl/Cmd + `

    6. Terminal opens at your last working directory

    7. Navigate to Project 

      cd ~/projects/my-app

    8. Submit Prompt to Claude 

      claude "Add input validation to the login form"

    9. Task Created Automatically

    10. New task appears in "To Do" column

    11. Task card shows your prompt and git context

    12. Monitor Progress

    13. Task moves to "In Progress" when Claude starts editing
    14. Watch as files are modified

    15. Approval modals appear for dangerous operations

    16. Review Changes

    17. Task moves to "Awaiting Input" when Claude pauses
    18. Click "View Diff" to see changes

    19. Review SonarLint issues if any

    20. Provide Feedback

    21. Continue conversation with Claude if needed

    22. Request modifications or ask questions

    23. Complete Task

    24. When satisfied, drag task to "Done"
    25. Commit changes in terminal: 
      git add .
git commit -m "Add input validation to login form"
git push

    Epic-Based Feature Development¶

    Use epics to organize development of large features.

    Scenario: Building User Authentication¶

    1. Create Epic
    2. Click "New Epic" button
    3. Title: "User Authentication System"

    4. Description: "Implement complete user authentication with login, signup, and password reset"

    5. Break Down into Tasks Submit separate prompts for each component: 

      claude "Create user database schema with migrations"
claude "Implement login API endpoint with JWT"
claude "Add signup form component with validation"
claude "Create password reset email flow"

    6. Link Tasks to Epic

    7. As each task is created, link it to the epic
    8. Drag task cards onto epic card, or

    9. Edit task and select epic from dropdown

    10. Track Progress

    11. Epic card shows aggregate status
    12. Progress bar indicates completion

    13. Total token cost displayed

    14. Generate Summary

    15. Once all tasks complete, click "Generate Summary" on epic
    16. AI creates summary of all changes

    17. Edit summary and add notes

    18. Review as a Unit

    19. Review all task diffs together
    20. Check for consistency across tasks

    21. Verify all requirements met

    22. Complete Epic

    23. Move all tasks to "Done"
    24. Epic status automatically updates
    25. Close epic or archive

    Code Quality Review Workflow¶

    Use SonarLint to ensure code quality as Claude makes changes.

    Setup¶

    1. Enable SonarLint
    2. Settings → SonarLint
    3. Ensure SonarLint Bridge is running

    4. Configure quality profiles if using SonarQube

    5. Set Analysis Preferences

    6. Enable automatic analysis on file changes
    7. Choose languages to analyze
    8. Set severity threshold for notifications

    During Development¶

    1. Claude Edits Files
    2. SonarLint automatically analyzes changes

    3. Issues detected in real-time

    4. View Issues in Diff

    5. Click "View Diff" on task
    6. Issues shown inline with code

    7. Click issue for details

    8. Review Issue Details

    9. Type: Bug, Vulnerability, Code Smell
    10. Severity: Blocker, Critical, Major, Minor, Info
    11. Rule: SonarLint rule identifier
    12. Message: What's wrong

    13. Remediation: How to fix

    14. Request Fixes

    15. If issues found, ask Claude to fix: 

      > Fix the SonarLint issues in the UserController

    16. Re-Analyze

    17. SonarLint automatically re-analyzes

    18. Verify issues are resolved

    19. Accept Changes

    20. Once issues resolved, mark task as done
    21. Commit clean code

    Best Practices¶

    • Review Issues Promptly - Address issues while context is fresh
    • Prioritize by Severity - Fix blockers and critical issues first
    • Learn from Issues - Use as learning opportunities
    • Configure Rules - Disable noisy rules, enable important ones

    Tool Approval Workflow¶

    Control dangerous operations with the approval system.

    Scenario: Claude Wants to Modify Production Config¶

    1. Claude Requests to Write File
    2. Claude wants to edit config/production.yml

    3. PreToolUse hook intercepts

    4. Approval Modal Appears Shows:

    5. Tool: Write
    6. File: config/production.yml
    7. Content: Preview of changes

    8. Risk: High (production config)

    9. Review Request

    10. Read the proposed changes carefully
    11. Check if changes are appropriate

    12. Verify no secrets or sensitive data

    13. Options

    Approve - Changes are safe and correct - Click "Approve" button - Claude proceeds with write

    Modify - Changes need adjustment - Click "Modify" button - Edit content in modal - Click "Approve" to proceed with modified content

    Deny - Changes are incorrect or unsafe - Click "Deny" button - Claude stops operation - Explain issue to Claude

    Always Allow - Trust Claude for this file - Check "Always allow writes to this file" - Click "Approve" - Future writes to this file auto-approved

    1. Continue Development
    2. Claude proceeds based on your decision
    3. Approval decision logged for audit
    4. Task continues

    Approval Configuration¶

    Customize which operations require approval:

    1. Settings → Approvals
    2. Toggle Tools
    3. Edit: Require approval for file edits
    4. Write: Require approval for new files
    5. Bash: Require approval for shell commands
    6. NotebookEdit: Require approval for notebook changes
    7. Set Timeouts
    8. How long to wait for approval (default 120s)
    9. Configure Auto-Allow
    10. Patterns that never require approval
    11. Example: *.test.js files always allowed

    Multi-Branch Development¶

    Work on multiple features simultaneously across branches.

    Scenario: Parallel Feature Development¶

    1. Branch A: Add Search Feature 
      git checkout -b feature/search
claude "Implement search functionality"
    2. Task created on "feature/search" branch

    3. Work tracked separately

    4. Switch to Branch B: Fix Bug 

      git checkout -b fix/authentication-bug
claude "Fix session expiration bug"

    5. New task created on "fix/authentication-bug" branch

    6. View Tasks by Branch

    7. Use branch filter in Kanban board
    8. See only tasks for selected branch

    9. Or view all branches together

    10. Switch Context

    11. Change branches in terminal
    12. Tasks automatically associated with correct branch

    13. Continue work on any branch

    14. Merge Workflow

    15. Complete tasks on feature branch
    16. Review all diffs
    17. Merge to main: 
      git checkout main
git merge feature/search
    18. Tasks remain associated with original branch

    Best Practices¶

    • Use Descriptive Branch Names - Easy filtering
    • One Epic per Branch - Link epic to branch
    • Review Before Merge - Check all tasks on branch
    • Clean Up - Archive or delete tasks after merge

    Token Budget Management¶

    Monitor and optimize Claude API costs.

    Setting a Budget¶

    1. Define Monthly Budget
    2. Example: $100/month for API costs

    3. Track spending throughout month

    4. Monitor Consumption

    5. Check token usage on task cards
    6. View consumption reports
    7. Compare against budget

    Daily Workflow¶

    1. Morning Check
    2. Open consumption report
    3. Review yesterday's usage

    4. Identify expensive tasks

    5. During Development

    6. Monitor task costs in real-time
    7. Badge on task card shows cost

    8. Adjust prompts if costs too high

    9. End of Day Review

    10. Total daily consumption
    11. Compare to daily budget ($100/30 ≈ $3.33/day)
    12. Identify trends

    Optimization Strategies¶

    Reduce Input Tokens - Keep prompts concise - Avoid including unnecessary context - Use Claude's memory features

    Use Cache Effectively - Let Claude cache common patterns - Reuse conversations when possible - Don't restart sessions unnecessarily

    Choose Right Model - Use Haiku for simple tasks - Use Sonnet for standard tasks - Use Opus only for complex reasoning

    Monitor Expensive Patterns - Identify prompts with high costs - Refine prompting strategy - Break large tasks into smaller ones

    Budget Alerts¶

    Set up notifications: 1. Settings → Notifications 2. Enable Budget Alerts 3. Set Thresholds - 50% of budget - 75% of budget - 90% of budget 4. Receive Alerts - Desktop notification - Email (optional)

    JIRA Integration Workflow¶

    Link Kintsugi tasks to JIRA tickets for project management.

    Initial Setup¶

    1. Configure JIRA
    2. Settings → JIRA
    3. Enter JIRA URL and credentials

    4. Test connection

    5. Verify Access

    6. Ensure you have access to projects
    7. API token must have read permissions

    Workflow: Building from JIRA Backlog¶

    1. Review JIRA Sprint
    2. Open JIRA board in browser
    3. Identify ticket to work on

    4. Note ticket key (e.g., "PROJ-123")

    5. Start Work with Claude 

      claude "PROJ-123: Implement user profile page"

    6. Include ticket key in prompt

    7. Kintsugi auto-detects and links

    8. Task Created with Link

    9. Task appears on board
    10. JIRA badge shows ticket key

    11. Click to open ticket in JIRA

    12. View JIRA Details in Kintsugi

    13. Click task card

    14. JIRA section shows:

      • Ticket status
      • Assignee
      • Priority
      • Description

    15. Work on Task

    16. Complete development as normal
    17. Task tracks progress in Kintsugi

    18. JIRA status remains separate

    19. Update JIRA Manually

    20. When task done in Kintsugi
    21. Update JIRA ticket status manually
    22. Add comment with link to commits

    Best Practices¶

    • Include Ticket Key in Prompt - Automatic linking
    • One Task per Ticket - Clear mapping
    • Sync Status - Keep JIRA updated
    • Add Work Logs - Link commits in JIRA comments

    Team Collaboration Workflow¶

    Use Kintsugi in a team environment.

    Scenario: Distributed Team¶

    1. Shared SonarQube Server
    2. All team members connect to same SonarQube instance
    3. Use shared quality profiles

    4. Consistent code standards

    5. Shared JIRA Project

    6. All tasks linked to JIRA tickets
    7. Team visibility into work

    8. Centralized project management

    9. Individual Development

    10. Each developer has own Kintsugi instance
    11. Tasks tracked locally

    12. Independent terminal and workflow

    13. Code Review

    14. Developer completes task
    15. Pushes branch to remote

    16. Creates pull request

    17. Reviewer Uses Kintsugi

    18. Reviewer clones branch
    19. Views task in their Kintsugi
    20. Reviews diff and SonarLint issues

    21. Checks token usage (cost efficiency)

    22. Approval and Merge

    23. Reviewer approves in git
    24. Branch merged to main
    25. JIRA ticket closed

    Team Best Practices¶

    Standards - Naming Conventions - Consistent epic and task names - Branch Strategy - Agreed git workflow - Quality Rules - Shared SonarQube profiles - Documentation - Use task comments

    Communication - Daily Standups - Reference Kintsugi task IDs - Status Updates - Update JIRA with Kintsugi progress - Code Reviews - Share diffs from Kintsugi - Retrospectives - Review token usage patterns

    Shared Configuration - SonarQube URL - Team server - JIRA Instance - Team instance - Quality Profiles - Synchronized - Approval Rules - Consistent settings

    Onboarding New Projects¶

    Add a new project to Kintsugi.

    Steps¶

    1. Clone Repository (if not local)
    2. Use Kintsugi's built-in clone feature

    3. Or clone manually: 

      cd ~/projects
git clone https://github.com/company/new-project.git

    4. Add to Kintsugi

    5. Settings → Repositories
    6. Click "Add Repository"

    7. Select directory or let Kintsugi scan

    8. Configure Project

    9. Set default branch
    10. Configure SonarQube binding (if applicable)

    11. Link JIRA project (if applicable)

    12. First Task

    13. Open terminal
    14. Navigate to project 
      cd ~/projects/new-project

    15. Start work: 

      claude "Analyze the codebase structure"

    16. Explore and Document

    17. Use Claude to understand codebase
    18. Tasks capture exploration
    19. Create epic "Onboarding - Project Name"

    Troubleshooting Development Issues¶

    Use Kintsugi to debug and fix issues systematically.

    Workflow¶

    1. Identify Issue
    2. Bug report from user
    3. Test failure

    4. Production error

    5. Create Investigation Task 

      claude "Investigate why user login is failing on mobile"

    6. Claude Investigates

    7. Reads relevant files
    8. Analyzes logs

    9. Identifies root cause

    10. Review Findings

    11. Check diff for files Claude examined
    12. Review SonarLint issues

    13. Check task comments

    14. Create Fix Task 

      claude "Fix the mobile login bug by adjusting viewport handling"

    15. Link Tasks

    16. Link investigation and fix tasks

    17. Or group under "Bug Fix" epic

    18. Verify Fix

    19. Review changes in diff
    20. Check SonarLint issues resolved

    21. Test manually

    22. Document

    23. Add comment explaining root cause
    24. Note prevention strategy
    25. Link JIRA ticket if applicable
